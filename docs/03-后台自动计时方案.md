# 「App 关着也自动计时」方案调研与实现

> 需求：耳机连上就自动开始计时，**不管 App 是否打开、是否在后台**。
> 结论：能实现，但只有一条路径真正满足；其余两条都有硬限制。

---

## 一、先纠正我上一版的说法

上一版我写「iOS 不给第三方 App 蓝牙连接状态，`routeChangeNotification` 只在 App 活着时送达」，这句话本身没错，但**结论下得太早**：它只描述了路 A 的失败，漏掉了路 C。

真正该说的是：**观察不到 ≠ 无法被唤醒**。iOS 给了第三条路，而且 Apple 官方文档明确支持它。

---

## 二、三条路，逐条查证

### 路 A · `AVAudioSession` 路由监听 —— ❌ 不满足

`AVAudioSession.routeChangeNotification` 只在进程存活时送达，App 被杀后无补发。

**唯一能让它「一直活着」的野路子是播静音音频维持 `audio` 后台模式**，开源库 [BackgroundKeeper](https://swiftpackageindex.com/timi2506/BackgroundKeeper) 就是这么干的，但它自己的 README 写着：

> **WARNING: This is not allowed by Apples App Store Guidelines**

Apple DTS 在 [开发者论坛](https://developer.apple.com/forums/thread/776949) 也直接回答过类似问题：`audio` 后台模式只允许真正的音频播放用途，为挂后台而播静音会被检测到并拒审。**这条路对要上架的 App 直接排除。**

### 路 B · CoreBluetooth 状态恢复 —— ⚠️ 对 AirPods 无效

技术上存在：`CBCentralManagerOptionRestoreIdentifierKey` + `bluetooth-central` 后台模式，系统能在 App 被回收后把进程拉起来跑一段（[TN3115](https://developer.apple.com/documentation/technotes/tn3115-bluetooth-state-restoration-app-relaunch-rules)）。

但有三个致命的附加条件：

| 条件 | 影响 |
|---|---|
| **AirPods 建立经典蓝牙（A2DP）连接后停止 BLE 广播** | 扫描侧收不到「已连接」事件。[抓包分析](https://cloud.tencent.cn/developer/ask/sof/320834) 原话：「连接后没有新的 BLE 数据包被拾取」 |
| TN3115：**用户从多任务上滑强制退出后，永不重启** | 用户杀一次 App 就永久失效 |
| TN3115：**iOS 26 起只有经 `AccessorySetupKit` 配对的配件才会触发重启** | AirPods 是系统配对的，第三方 App 无法用 ASK 接管它 |

Stack Overflow 上有人实测过同类需求（[79070195](https://stackoverflow.com/questions/79070195/ios-how-to-be-notified-when-a-ble-device-is-connected-to-the-phone)）：前台能看到连接/断开，**后台只能看到断开**，因为后台不会持续扫描。

> 但这条路对**非苹果 BLE 耳机**（Sony / JBL / Bose / Nothing 等自家 App 控制的）有效。已作为可选通道实现，见下文。

### 路 C · 快捷指令「蓝牙」个人自动化 + AppIntent —— ✅ 唯一可行

Apple 官方支持文档 [在 iPhone 上启用或停用个人自动化](https://support.apple.com/en-cn/guide/shortcuts/apd602971e63/7.0/ios/17.0) 明确列出：

> 以下自动化可以自动运行：特定时间、闹钟、CarPlay 车载、**无线局域网**、**蓝牙**、Apple Watch、体能训练……

且：

> 关闭「运行前询问」，然后轻点「不询问」。**触发该自动化时将不会通知你。**

配合 AppIntent 的 `openAppWhenRun = false`，intent 在**纯后台进程**里执行，不唤起界面、不需要 App 在前台（[App Intents 实践](https://github.com/omarshahine/homeclaw/blob/d4d2e0adf4d111ebcb88f5a8d470b8413c096226/.claude/skills/ios-app-intents/references/example-patterns.md)）。

**这就是要的答案：戴上耳机 → 自动化触发 → intent 写库 → 用时统计有了。整个过程中 App 可以完全没打开。**

官方文档里「不能自动运行」的触发器里没有蓝牙，这条确认过两遍。

## 三、我上一版实现的致命 bug

上一版 `StartTrackingIntent` 只做了这件事：

```swift
defaults.set(Date.now.timeIntervalSince1970, forKey: SharedDefaults.Keys.shortcutStart)
```

**只是丢了个时间戳，真正的 `SessionRecord` 要等 App 下次被打开时由 `reconcile` 补出来。**

后果：用户配好自动化、天天戴耳机、但一周不打开 App → 打开时只会补出**一条**记录（开始时间是最早那个时间戳，结束时间是最后一次心跳），中间所有会话全丢。这等于没实现需求。

**已修复**：intent 现在直接建独立 `ModelContainer` 写数据库。

关键约束（App Intents 的硬性要求）：

> intent runs OFF your app's process, on the system's schedule, possibly while the app is terminated — **so it must construct its own store access**

所以 `SharedSessionStore` 每次调用都新建容器指向同一个 App Group SQLite，不能依赖 `SessionEngine.shared`（那个单例此时可能根本不存在）。

## 四、当前实现的三层架构

```
┌─ Tier 1 · 快捷指令蓝牙自动化 ──────────── 精确，App 不用运行
│  连接 → StartTrackingIntent  → SharedSessionStore.begin() 写库
│  断开 → StopTrackingIntent   → SharedSessionStore.end()   收尾
│  精度：亚秒（仅自动化调度延迟）
│
├─ Tier 2 · AVAudioSession 路由 ─────────── 精确，但仅 App 存活时
│  routeChangeNotification → SessionEngine
│  与 Tier 1 并发时自动去重，来源升级为 live
│
└─ Tier 3 · CoreBluetooth（可选）────────── 仅非苹果 BLE 耳机
   BLEPresenceWatcher + 状态恢复
   AirPods 上静默失效，不影响主流程
```

### 去重与优先级

同一次连接可能被多个通道看到，`SharedSessionStore.begin()` 的做法：

- 已有未结束记录 → **复用**，只把开始时间取更早的、来源升级（`shortcut` → `live`）
- 没有 → 新建

### 不该被推断收尾的会话

修了一个连带问题：`reconcile` 原来会把「自动化 / 手动开出来的会话」当成泄漏记录按心跳砍掉。现在 `source == .shortcut || .manual` 的会话**只在超过 12 小时**时才视为泄漏。

## 五、用户侧的配置（这是产品能否成立的关键）

自动化必须用户自己配（App 无权代劳），所以做成了**首次启动的全屏引导**，5 步：

1. 为什么要多一步（讲清 iOS 限制）
2. 建自动化 + **关「运行前询问」**
3. 加「开始记录耳机时长」动作
4. 再来一遍做「结束记录」
5. 打开快捷指令

设置页顶部还有**自动化状态徽章**，用「最近一次会话的 source」反推：

| 徽章 | 含义 |
|---|---|
| 🟢 已生效 | 最近一条是蓝牙自动化记的 |
| 🟡 未配置 | 只在 App 打开时才记得到 |
| 🟡 待确认 | 最近一条是推算/手动 |

比让用户自己猜「我配成功了吗」有用得多。

## 六、必须承认的残留限制

即使全部做对，仍有做不到的事：

| 限制 | 原因 | 影响 |
|---|---|---|
| 用户**上滑强杀** App 一次 | TN3115 | 自动化本身仍在（快捷指令是独立进程），Tier 1 **不受影响**；受影响的只是 Tier 2/3 |
| 用户忘了配自动化 | 产品引导问题 | 只剩 Tier 2，App 不在时不记 |
| AirPods 深度睡眠后自动化偶发不触发 | 系统行为 | 会出现「漏记一次」 |
| 「连接」≠「佩戴」 | 摘一只耳机仍保持连接 | UI 统一写「连接时长」 |
| App Store 审核可能要求说明蓝牙用途 | 已加 `NSBluetoothAlwaysUsageDescription` | 描述写清楚即可 |

**其中第 1 条要特别说明**：这是 Tier 1 相比 Tier 2/3 的最大优势——快捷指令自动化跑在系统进程里，**用户杀 App 不影响它**。这也是为什么主通道必须放在这里。
